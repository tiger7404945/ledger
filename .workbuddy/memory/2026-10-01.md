### ⚠️ 顺带查出一个真实缺陷（未修，待裁决）

实验中新匿名账号（MKdmO）**分区落在 `ledger_anon`** 而不是 `ledger_<uid前缀>`。
追因：`initDataLayer()` 用 `cloud.getIdentity()` 取 uid，而它**不触发登录**（设计如此，防 88 次写入），
所以「设备上没有任何身份缓存」时 uid=null → 分区 `ledger_anon`；随后 `ensureCloudFirstBind()`
才 `ensureSignedIn()` 创建匿名账号拿到 uid，**但分区不跟着重建**。

后果链（本次实测坐实）：`ledger_anon` 是老库、带着上个会话的 `syncWatermark=1790829629921`
→ `ensureFirstBind` 命中 `if (watermark) { set(doneKey, Date.now()); return 'already-synced' }`
→ **一条都不入队、不推送**。证据：`firstBindDone=1790832253971` 正是清空时刻（1790832253）+971ms，
即 `already-synced` 分支写下的；该账号云端 **0 条**、outbox **0 条**。
⇒ **这条路径下用户的账目只在本机，云端零备份；此时清浏览器数据 = 永久丢失。**

三个衍生问题（都待修）：
1. **水位线不能证明「当前账号」推过**：它只证明「某个账号在这台机器的这个分区推过」。
   （修法方向：分区名 ≠ `ledger_<accountPrefixOf(uid)>` 时，水位线不可信，应强制走 `pushLocal`。）
2. **`ledger_anon` 是跨身份共享库**：任何「启动时拿不到 uid」的会话都会读它 → 串号风险。
3. 首次访问落 `ledger_anon`、第二次访问落 `ledger_<前缀>`（空库）→ 用户会莫名撞上一次
   首绑裁决弹框，且旧库留成孤儿。

**实验卫生**：这类"清身份"实验必须先把身份键备份到 **sessionStorage**（`localStorage.clear()`
清不到它，重载也保留），否则旧身份的 88 条云端数据会变成永久孤儿（PRIVATE 权限下谁也读不到）。
MKdmO 那个新账号是实验副产品，云端 0 条、无数据，未做处理。
