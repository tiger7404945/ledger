## S2 技术设计定稿（未实施，已写入计划文档）

用户要求「先给 S2 的技术设计」。出了三张图（四态状态机 / 分层与 S3 替换点 / 单次 sync 流程），

### 用户的两处关键质疑（都促成了设计深化）
1. 「测试用例里是否考虑到了多用户之间数据隔离以及同用户不同终端之间数据同步、互斥」
   —— 原设计确实没覆盖，是真实缺口。补出「隔离 / 同步 / 互斥」三维度拆分。
2. 由此推出**核心概念澄清**：无中心锁时跨终端的「互斥」做不到也不该做，目标是**收敛**。
   单设备内互斥靠防重入即可；跨终端只能保证「并发写后两端收敛到同一状态」。

### 定稿的设计要点
- **状态机四态**：`idle / syncing / error / offline`（计划原写三态，实施加 offline：
  离线时不发请求，省 CloudBase 资源点也不污染 retry 计数）。**防重入是唯一闸门**——
  `syncing` 期间再调 `sync()` 必须返回同一个 in-flight Promise，而不是 return（否则调用方
  拿不到结果也没法 await）。
- **同步顺序 pull 在前、push 在后**：否则本地的旧版本会覆盖云端的较新版本，另一台设备的修改被无声抹掉。
- **push 必须是「条件 upsert」**，且返回 `{ upserted, rejected }`。**`rejected` 是关键**：
  云端因「你这份更旧」而拒绝时若不回话，本地会以为推成功、两端悄悄分叉；收到 rejected 要立即补一次 pull。
- **push 推「当前本地的文档」，不是入队时的 payload 快照**（否则被否决的旧快照会被原样推回去）。
- **fakeCloud 必须带身份维度**（`cloud.as('user_b')`），否则两个用户的数据躺在同一 Map 里，
  测出来天然全通毫无意义。能测「代码没把身份抹掉」，**测不了**真实安全规则（那是 S3 验收第 3 条）。
- **真正的串号风险在本地不在云端**：两个账号共用一个 `ledger` 库时，B 能看到 A 的账，
  且 A 残留的 outbox 条目会被推到 B 名下。建议「库名分区」（`ledger_<openid>`），S2 只预留
  （库名可注入，`openDB({ dbName })` 在 S1 已支持），S5 启用。
- **outbox 改为依赖注入的存储后端**（`memory` / `idb`），搬进 IndexedDB；
  为此需把 `openDB()` 与 store 原语抽到 `src/api/core/idb.js`，**否则循环依赖**
  （outbox 要用 openDB，而 idbAdapter 又 import outbox）。
- **接口留好 S4 的位置**：`pull` 带 `cursor`/`limit`/`hasMore`；`serverTime()`；
  fakeCloud 提供 `_skew(ms)` 模拟时钟偏移——**只记录行为不做断言**，把「新者胜依赖客户端时钟」
  这个问题暴露给 S4，避免 S2 变成假装解决了时钟问题的骨架。
- **验收脚本 17 组用例**（原计划 4 条）。真正会咬人的是 5/8/13/15：防重入、否决回拉、
  双实例收敛、拒绝后回拉——都只能在多实例/并发场景暴露，单设备手点永远测不出来。

## 实测：`@cloudbase/js-sdk` vs `@tencent-ai/workbuddy-cloud-sdk`（用户要求验证）

用户质疑第二个「看起来是给 AI agent 用的、不像给传统 web 应用」。**实测结论：质疑不成立**，
它是标准的浏览器 BaaS 客户端；但用户的直觉有合理来源，且暴露了一个真问题（见下）。

### 依据一：包形态
- `@cloudbase/js-sdk@3.10.1`（2026-09-23 发版，另有 4.0.x alpha）—— 成熟，按运行环境分流
  (`exports["."].node` 单独给 `index.node.esm.js`)。
- `@tencent-ai/workbuddy-cloud-sdk@0.1.3`（6 天前发版，另有 `dev` 频道）—— **很年轻**。
  有 `lib/index.global.js` UMD 浏览器产物（`unpkg`/`jsdelivr` 字段 + `./global` 子路径）
  和 `miniprogram_dist` + `./miniprogram` 子路径；零依赖。
- 实测 `index.global.js` 里 Node 专有 API（`node:` / `fs` / `process.env` / `__dirname` / `child_process`）
  **命中数全为 0** —— 浏览器产物干净。

### 依据二：运行时 API（Node 里真实 import）
- workbuddy SDK 顶层 22 个导出；`WorkBuddyCloudClient` 成员 `database / auth / storage / llm`。
  - `auth` 是**终端用户**认证：`signUp` / `signInWithPassword` / `sendOtp` / `signInWithOtp` /
    `verifyOtp` / `signInWithOAuth` / `resetPasswordForEmail` / `getSession` / `refreshSession` /
    `onAuthStateChange` / `signOut`，外加 `oauthRelayBaseUrl` 支撑**网页微信扫码登录**。
  - `database` 是 PostgREST/supabase-js 风格：`from(table).select()...`、`rpc()`、`{data,error}` 信封。
  - `storage`：`from` / `userPath` / `sharedPath`。`llm`：`models` / `chat`（仅 4 模块之一）。
- **浏览器优先是写死的设计**：`endpoint` 可省略（默认 `location.origin`）；
  在 Node 里省略会抛 `WorkBuddyCloudConfigError: endpoint is required outside browsers
  (no location.origin to fall back to)`。会话持久化的注释原话是「**localStorage 是唯一真源**」。

### 依据三：决定性对打（同一 endpoint，两 SDK 各读一次库）
| | workbuddy SDK | `@cloudbase/js-sdk` |
|---|---|---|
| 实际请求 | `expense-tracker-67402.app.workbuddy.host/.cloud/database/rest/bills?select=*&limit=1` | `expense-tracker-67402.**api.tcloudbasegateway.com**/v1/database/instances/(default)/databases/(default)/collections/bills/documents` |
| 结果 | 404 `DATABASE_PGRST205` "Could not find the table 'public.bills' **in the schema cache**" | 404 + `INVALID_ENV` |
| 含义 | 协议/鉴权都通过，只是表没建 → **真答到了 PostgREST 后端** | **根本没打到我们的 endpoint** |

- `@cloudbase/js-sdk` 的主机是 **`{envId}.api.tcloudbasegateway.com` 写死拼接**；
  其 `init` 配置字段只有 `env`(+`region`/`accessKey`/`secretId`/`secretKey`/`persistence`/`debug`/
  `timeout`/`throwOnCode`/`lang`)—— **没有 `endpoint`/`host`/`baseUrl`**，结构上无法改指向。
- 它在包里对 `workbuddy` / `publishableKey` / `x-wb-webapp-access-key` 的命中数**全为 0**。
- `app.rdb()`（官方文档说的「新路径」）同样打到 `...api.tcloudbasegateway.com`；
  且它在 Node 里还会去请求 **`metadata.tencentyun.com`**（腾讯云实例元数据服务，自动发现凭据）
  —— **这反而是服务端/基建侧行为**，workbuddy SDK 里没有。用户对「谁是服务端向」的直觉是反的。

### 依据四：endpoint 鉴权模型（curl 实测）
- 无 key → `401 {"error":"invalid_client",...}`（**OAuth 2.0 错误码**）
- 正确 key → `200`
- 正确 key + 伪造 Origin → `403 {"error":"access_denied","error_description":"the request origin is not allowed for this client"}`
- 无 key + 正确 Origin → `401`
- 但 **`Origin: http://127.0.0.1:5173` 与 `http://localhost:5173` 都返回 200** —— 本地 dev 开箱可用。
- `/.cloud/storage/` → `401 MISSING_CREDENTIALS`，错误体带 **CloudBase 原生错误码 + docs.cloudbase.net 链接 + requestId**
  → 证明「WorkBuddy 网关（OAuth 风格）+ 底层 TCB/CloudBase（原生错误）」两层架构。

### 依据五：官方文档自己也把两者对立起来
- 内置 `cloud-service` skill 的 `references/database/code-generation.md` 原话：
  「Do **not** reach for `@cloudbase/js-sdk`, `app.rdb(...)`, `tcloudbasegateway.com`...
  the app talks only to `@tencent-ai/workbuddy-cloud-sdk`」，且标题是
  "Integrate the cloud service database into a **published** app"（给已发布应用写数据访问代码）。
- 同时项目里还有另一套 skill `.agents/skills/cloudbase/`（GitHub `tencentcloudbase/cloudbase-skills`
  v2.34.6），它推荐 `@cloudbase/js-sdk`（29 个文件）且 **0 次**提到 workbuddy SDK。
  其中 `relational-database-web-cloudbase` 自带 `[Deprecated]` 标记，注释指向
  `postgresql-development-cloudbase`（该文档提 `app.rdb()` 32 次）。
- **结论：两者是同一底层 CloudBase PostgreSQL 的两条入口，必须二选一、不能混用。**
  - `@cloudbase/js-sdk` → 用户自己的腾讯云环境（envId + tcloudbasegateway.com），成熟但需手工准备。
  - `@tencent-ai/workbuddy-cloud-sdk` → WorkBuddy 托管环境（应用域名 `/.cloud/**` + publishableKey + Origin 绑定），零运维但绑平台。
- 因此**先前记的「S3 需用户先做 P1–P9 前置准备」对内置路径不成立**——内置路径不需要那些。

### 真实风险（用户直觉的合理内核）

3. 所以「选它」是拿**零运维**换**成熟度 + 可移植性**。

## 第二轮深挖：`@cloudbase/js-sdk` vs workbuddy SDK（用户带了第三方 AI 的答复来质疑）

用户贴了豆包的一份答复（`doubao.com/thread/xTTihPOuXp4uecL4U`），那份答复的核心结论**说反了**。
我做了三层新的实测（URL 重写实验、请求头逐字节对比、auth 端点探测），把差异钉到架构层。

### 一句话结论
**两者都是 CloudBase 客户端 SDK，底层是同一个服务**（CloudBase 关系型数据库 = PostgreSQL + PostgREST）。
差别在**进入这个服务的入口与鉴权模型**，不在功能范围。豆包的「一个是 BaaS、一个是 Agent SDK」
这个二分法是错的。

### 硬证据 1：`/.cloud/database/` 的 404 自白
`GET /.cloud/database/` → `404 {"code":"INVALID_PATH","message":"Invalid path. PostgREST only serves /v1/rdb/rest ..."}`
→ **后端自己承认底层是 PostgREST**，且网关 `database → /v1/rdb/rest/**` 的映射真实存在
（`/v1/rdb/rest/` 直连 404，必须经网关）。
`/.cloud/database/documents/` → 404 → **这个环境只有关系型，没有文档型**。

### 硬证据 2：URL 重写实验（`probe-rewrite.mjs`）
把 js-sdk 的 `{envId}.api.tcloudbasegateway.com/v1/rdb/rest/bills?...` 重写为
`{appDomain}/.cloud/database/rest/bills?...` 并注入 `x-wb-webapp-access-key` 后：
- 错误从 `INVALID_ENV` 变成 **`401 invalid_grant: the session is invalid, expired or issued for another client`**
  → **请求真的抵达了 WorkBuddy 网关的鉴权层**，证明两套路径指向同一后端。
- 但仍不成功 —— 原因见证据 3。

### 硬证据 3：请求头逐字节对比（`probe-headers.mjs`）
| | workbuddy SDK | `@cloudbase/js-sdk` |
|---|---|---|
| 读库请求头 | **只有** `x-wb-webapp-access-key` | `authorization: Bearer undefined` + `x-tcb-region` / `x-tcb-source` / `x-sdk-version` / `x-client-timestamp` |
| 前置握手 | **无** | **必须先 `POST {envId}.api.tcloudbasegateway.com/auth/v1/token/clientCredential` 换 token** |

### 硬证据 4：网关**故意不暴露** clientCredential（curl 实测）
| 端点 | 带 key | 不带 key |
|---|---|---|
| `POST /.cloud/auth/v1/token/clientCredential` | **404 `invalid_request: the requested endpoint is not available`** | 401 `invalid_client` |
| `POST /.cloud/auth/v1/token` | **401 `invalid_grant`**（端点存在） | — |
| `GET /.cloud/auth/v1/settings` | 404 不可用 | — |

→ 网关**先验 key（错就 401）、再答端点不存在（404）**。也就是：**js-sdk 赖以启动的那次握手，
WorkBuddy 网关刻意不提供**。所以 js-sdk 结构上无法用于这个环境（它没有 `endpoint`/`host` 配置项，
唯一能改指的手段就是上面那个会被 404 掉的实验）。

### 硬证据 5：workbuddy SDK 的认证模型（`probe-auth.mjs`）
- `POST {appDomain}/.cloud/auth/v1/signin` `{username,password}` → 假账号返回
  `400 invalid_username_or_password`（CloudBase 原生错误码）→ **真实用户登录后端是活的**。
- 只带 publishableKey、**无 session** 就能读库（拿到 `PGRST205`），`authorization` 头为空。
- `cloud.auth.getSession()` → `{data:null, error:null}`；`anonymousTokenProvider()` 返回 `undefined`
  → 它是个钩子，**不是匿名登录**。官方文档明写「Anonymous login is deliberately not part of the auth surface」。
- `user_list_end_users` 返回 `[]`（尚无终端用户，符合预期）。

### 硬证据 6：workbuddy SDK 里**根本没有 Agent 概念**
`agent` / `Agent` / `tool_call` / `toolCall` / `workflow` / `knowledge` / `assistant` 在
`lib/index.js` 里出现次数**全部为 0**。它的 `llm` 模块只有 `/chat/completions` + `/models`
（朴素 OpenAI 兼容 chat）。且它 136 处出现 `supabase`、引用 `@supabase/postgrest-js` /
`@supabase/supabase-js` → **它是 supabase-js 的改铸版**。
而 `@cloudbase/js-sdk` 里 `postgrest` 出现 **0 次**，其 `app.rdb()` 是**自写客户端**。

### 豆包那份答复的逐条核对（用于日后遇到同类说法）
| 它的说法 | 实测 |
|---|---|
| workbuddy SDK「只负责 AI 对话、Agent 任务调用」 | ❌ `agent` 出现 0 次 |
| 「不操作云数据库 / 不能直接读写 CloudBase 数据库」 | ❌ 实测直接发出 PostgREST 请求并拿到 `PGRST205` |
| 「不提供数据库、存储、登录能力」 | ❌ 四个模块就是 database / auth / storage / llm；`signin` 实测可用 |
| 「AI 访问数据库是 Agent 内部通过 MCP 连接器调用」 | ❌ 前端 SDK 直接操作 db，与 Agent 无关 |
| 「WorkBuddy SDK 体积更大，纯业务页面没必要引入」 | ❌ 反而小 3 倍：UMD **61 KB** vs 721 KB；tarball 1.09 MB vs 5.86 MB |
| 「两者可以搭配使用」 | ❌ 是**同一个库的两套入口**，混用互相打架；内置文档明令「不要 reach for `@cloudbase/js-sdk`」 |
| 「必须绑定 env / 可选」 | ⚠️ 两边都必须绑，只是绑的东西不同（envId vs endpoint+publishableKey） |
| 「WorkBuddy 是独立 Token 计费」 | 未验证，不置评 |

**它错在哪**：把「**WorkBuddy 这个平台**是 Agent 平台」与「**workbuddy-cloud-sdk** 是 Agent SDK」
混为一谈。SDK 的职责是给「由 WorkBuddy 生成/托管的**应用**」提供一个后端 —— 这是 BaaS，不是 Agent 客户端。

## 第三轮：用户拿腾讯云 CloudBase 官方 Agent 的答复来对撞（我方结论与官方答复的仲裁）

用户问了 CloudBase 官方 Agent「两个 SDK 区别，Web 前端对接后台数据用哪一个」，官方答：
「Web 前端用 `@cloudbase/js-sdk`；`@tencent-ai/workbuddy-cloud-sdk` 是 WorkBuddy AI IDE 的集成包，
AI IDE 工具链内部使用，不是给业务前端调用的。」

**仲裁结论：官方答复在「自有 envId」前提下正确，但它对 workbuddy SDK 的性质判断是错的**
（它自己标了置信度 0.75，并写明「未在 CloudBase 官方文档中详细公开，以上分析基于 WorkBuddy
作为 AI IDE 的定位」——是推断不是事实）。错因：把「**WorkBuddy 是 AI IDE 平台**」投射成
「**workbuddy-cloud-sdk 是这个 IDE 的 SDK**」。

### 关键：官方内置文档有**明文**裁决（这是我方结论的权威依据，比实测更硬）

| 出处 | 原文 |
|---|---|
| `cloud-service/SKILL.md:273-274` | "The underlying environment id and all provider keys stay **server-side and are never returned**. If a pattern seems to require the front end to hold a long-lived key, the pattern is wrong." |
| `cloud-service/SKILL.md:314-317` | "The client is `@tencent-ai/workbuddy-cloud-sdk` … Do **not** initialize a second CloudBase client or hand-write module fetch wrappers." |
| `references/database/code-generation.md:10` | "Do **not** reach for `@cloudbase/js-sdk`, `app.rdb(...)`, …" |
| `references/auth/code-generation.md:50-51` | "Use `@tencent-ai/workbuddy-cloud-sdk`. Do **not** initialize `@cloudbase/js-sdk` separately and do not call `/.cloud/auth/**` with hand-written `fetch`." |
| `references/auth/management.md:13-14` | "**Never accept an `envId`**, TCB key, COS key or service-role credential from the caller; the server resolves **Application → Environment**." |

**→ 这就把问题钉死了：envId 是「设计上不下发」，不是「我没找到」。**
服务端用 `Application → Environment` 自解析，前端只拿 `endpoint + publishableKey`。
js-sdk 的必填 `env` 我们**无从填起** —— 结构上不可用，不是配置问题。

**→ 真正的判据不是「哪个 SDK 更好」，而是「这份数据住在哪个环境」**：
- 数据住在**你自己建的 CloudBase 环境**（envId 你可见）→ `@cloudbase/js-sdk`。官方答复适用。
- 数据住在 **WorkBuddy 托管的应用环境**（`wbapp_*`，envId 服务端持有）→ `@tencent-ai/workbuddy-cloud-sdk`。本项目属此类。

### 新增实测（本轮）
- 响应头出现 **`Server: tcbgw`** + `X-Cloudbase-Request-Id` / `X-Cloudbase-Upstream-Status-Code`
  → 应用域名前面就是**官方 CloudBase 网关（TCB Gateway）**，不是 WorkBuddy 自研的东西。
- PostgREST swagger 的 `host: 0.0.0.0:3000` → 后端是容器里的 PostgREST，铁证关系型。
- `/.cloud/database/rest/rpc/get_env` → `DATABASE_PGRST202`（函数不存在）→ 仍是 PostgREST 在答。
- **域名前缀不是 envId**：`expense-tracker-67402.api.tcloudbasegateway.com/v1/rdb/rest/` →
  `404 INVALID_ENV`；`my-cloudbase.api.tcloudbasegateway.com` 同样 `INVALID_ENV`
  （通配 DNS 全解析到网关，不存在的 env 一律 `INVALID_ENV`）。→ 别再拿域名前缀当 envId 试。

### ⚠️ 顺带挖到两条对 S3 影响很大的约束（此前不知道）
出自 `cloud-service/references/auth/code-generation.md`：
1. **Web 应用只支持邮箱登录**（L20-27）：Email OTP / Email+密码 = yes；**Phone(SMS)=no、
   微信登录=no**（这两项仅微信小程序）。**且没有匿名登录** —— L33 明写 "Do **not** generate
   anonymous login…"，L153 "Anonymous login is deliberately not part of the auth surface"。
2. **auth 只在应用已注册的 HTTPS 发布域名上可用**（L40-42）："WorkBuddy preview and localhost
   are **not supported** because they do not have the registered Origin/callback binding."
   → **本地 `127.0.0.1:5173` 无法完成登录**（数据面 `/.cloud/database/rest/` 实测 localhost 是 200，
   但那只到 schema 层；真正读写带 RLS 的表要 session）。
   → **S3 的云端同步只能在「发布到 release 域名」后验证**，本地开发验证不了登录/同步。
   这与本项目 local-first 架构不冲突（本地照常可用），但**排期上要考虑「必须先发布」**。

### 待用户拍板（未变，但论据更充分）
- **(A)** WorkBuddy 托管 + workbuddy SDK：零运维、环境已开、localhost 数据面已验证连通；
  代价 = SDK 0.1.x + 绑平台 + **必须做邮箱登录页** + 只能在发布域名上验同步。
- **(B)** 自有 CloudBase 环境 + js-sdk：官方 & 成熟（3.10.1）、可移植、**有匿名登录**（对个人
  记账 App 友好，免登录墙）；代价 = 要手工建环境、配安全来源、且需先把 envId 给我。
- **唯一未解变量**：用户控制台里的「体验版」环境与本托管应用**是否同一个底层**。拿不到 envId
  无法自证；若用户给出控制台 URL 里的 `envId=xxx` 可实测 js-sdk 能否读同一份数据。

## 第四轮：用户给出了自己的 envId，实测（决定性）

用户给出：环境名 `my-cloudbase`，**envId `my-cloudbase-********`**（体验版）。
用 curl + `@cloudbase/js-sdk` 真打了一遍（探针 `.preview/sdk-probe/probe-userenv.mjs`，可重跑：
`node probe-userenv.mjs "<Origin>"`，省略 Origin 即模拟 Node）。

### 结论 A：**用户的环境是真实存在且可用的**，`@cloudbase/js-sdk` 能正常初始化它
- `{envId}.api.tcloudbasegateway.com/v1/rdb/rest/` → **`401 MISSING_CREDENTIALS`**（环境存在，缺凭据）；
  对照 `expense-tracker-67402.api.tcloudbasegateway.com` → **`404 INVALID_ENV`**（环境不存在）。
  **→ 判 env 是否存在的方法：`MISSING_CREDENTIALS` = 存在，`INVALID_ENV` = 不存在。**
- `cloudbase.init({ env: 'my-cloudbase-********' })` **成功**，模块齐全：
  `auth / database / rdb / mysql / storage / ai / models / callFunction / callContainer / realtime …`
- 响应头同样是 `server: tcbgw` → 同一个官方 CloudBase 网关，只是走 envId 域名入口。

### 结论 B：**js-sdk 启动所需的 `clientCredential` 握手，在用户环境上「存在」**
| 端点 | 用户自有环境 | WorkBuddy 托管应用 |
|---|---|---|
| `POST /auth/v1/token/clientCredential` | **`401 MISSING_CREDENTIALS`**（端点存在，等凭据） | **`404 the requested endpoint is not available`**（刻意不暴露） |
→ 这条把 A/B 分野钉死了：**js-sdk 结构上只能用于「自有 envId」这条路**。

### 结论 C：**安全来源（Origin）实测 —— 修正我上一轮的判断**
`probe-userenv.mjs` 注入不同 Origin 跑三轮，结果：

| Origin | 结果 |
|---|---|
| 无 Origin（Node） | `400 LOGIN_TYPE_DISABLED`（登录方式未开启）——**已过 Origin 校验** |
| `http://localhost:5173` | `400 LOGIN_TYPE_DISABLED`——**同样已过 Origin 校验** |
| `https://evil.example.com` | **`403`**（auth / rdb / database 三个端点全 403）——**Origin 校验生效** |

→ **`localhost:5173` 能过安全来源校验**，本地开发可用；伪造域名被拦。
（建议仍在控制台「安全配置 → 安全来源」里确认一下，并把未来发布域名加进去。）

### 结论 D：**匿名登录是「可开启的能力」，不是「没有」——修正我上一轮的判断**
`signInAnonymously()` 返回 `AuthError` `code: login_type_disabled`（errorCode **4045**），
引导文案原话：「请联系开发者在**身份源列表**开启匿名登录」+ 控制台路径
`https://tcb.cloud.tencent.com/dev?envId=#/identity/login-manage`。
→ 这**不是**「刻意不提供」，只是**默认未开启**。控制台开关一开即可用。
⚠️ 但注意：**匿名账号是「按设备」的身份，同一人在两台设备上会拿到两个 uid → 不能满足本项目
「多终端同步」的目标**。多终端同步最终仍需要一个真实身份（邮箱密码 / 手机号 / 匿名转正绑定），
这一点要在 S3 里再验证具体路径。

### 结论 E：用户环境**同时暴露文档型与关系型**（托管环境只有关系型）
- `app.database()` → `…/v1/database/instances/(default)/databases/(default)/collections/bills/documents`
  → `401 MISSING_CREDENTIALS`（**路径可达**，只是没 session）
- `app.rdb()` → `…/v1/rdb/rest/bills` → `401`（同上）
- 对照 WorkBuddy 托管环境：`/.cloud/database/documents/` → `404 INVALID_PATH`
→ 用户环境的控制台侧栏也确实同时有「SQL型数据库」与「文档型数据库」。
**→ 原计划想要「文档型（嵌套对象、免 JOIN）」的设计自由度在 B 路是保留的。**

### 结论 F：两套环境**几乎确定不是同一个**
- 托管网关只暴露关系型（`/.cloud/database/documents/` 404），用户环境两者都有；
- WorkBuddy 的 app key 在用户环境上不被接受（仍 401）；
- 托管应用的 envId 被设计为不下发，无法与 `my-cloudbase-********` 直接比对。
→ 要 100% 钉死，需在控制台开匿名登录后核一次数据（零成本，S3 本来就要开）。

### 由此更新的选型建议（**倾向 B，且理由比上一轮强得多**）
| | (A) WorkBuddy 托管 | (B) 自有 `my-cloudbase-********` + js-sdk |
|---|---|---|
| 环境 | 已开、已验证 | 已存在、已实测可 init |
| 登录 | 仅邮箱，**无匿名** | **匿名可开**（免登录墙），另有邮箱密码 |
| 本地开发 | **auth 只能在发布域名上用，localhost 不支持** | **`localhost:5173` 实测过安全来源** |
| 数据库 | 仅关系型 | **关系型 + 文档型** |
| SDK | 0.1.x、闭源、无 repository | 3.10.1、官方文档、公开 GitHub |
| 数据归属 | envId 都对你看不见 | **你自己的腾讯云账号** |
→ 待用户拍板。选 B 的话，用户侧只需三步：① 控制台开「匿名登录」；② 确认/添加「安全来源」
（`http://localhost:5173` + 未来发布域名）；③ 之后我按原计划的文档型设计建集合。
