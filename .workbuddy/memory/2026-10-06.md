  1. `cloudbaseAdapter.push()` 第 519 行 `await fetchServerStamps(...)`
     **没有接收返回值**，函数返回的仍是 `{ upserted, rejected }`（第 522 行），
     **不含 `stamps`**。而 `syncEngine.js:210` 读的是 `result.stamps`。
  2. 更深一层：**即使接住也用不了** —— `fetchServerStamps` 返回的 Map 其 key 是

  3. 测试为何全绿：`fakeCloud` 第 202 行 `stamps[id] = stamped` 用的是**本地 id**

     **返回值的 id 空间**上。
- **影响评估（不是丢数据 bug）**：刻度回写本地还有第二条路 —— 云函数盖刻度时
  顺带刷新了 `_serverTs`（index.js 第 220 行），下次 pull 必然重新拉到该文档
  （`_serverTs > 水位线`），`fromRemote` 保留 `serverUpdatedAt` → `applyRemote` 落库。
  只是**延迟一个同步周期**。且 `effectiveServerStamp` 的失效判据（内容比刻度新则
  刻度作废）让「本地暂时没刻度」不会导致误判。
- 结论：**冗余路径失效 + 契约漂移**，功能无碍。修法给了用户（接住 Map + 把 key 从
  别名映射回本地 id），**未擅自改代码**，等确认。

## 概念答疑：`_serverTs` 与水位线的关系

- 用户问「`_serverTs` 是水位线时刻吗？为什么每条记录都有而不是全局的」→ 答：**不是**。
  - **水位线**：`meta.syncWatermark`，**全库唯一一个整数**（`syncEngine.js:136` 读，
    `pullAll` 里三个集合共用同一个 `since`）。
  - **`_serverTs`**：云端**每条文档**各带一个，由客户端 `db.serverDate()` 在 `.set()` 时
    写入（`cloudbaseAdapter.js:503`，写指令由服务端求值，客户端伪造不了），
    推送时云函数会顺带刷新成同一时刻。
- 为什么必须逐条：增量过滤在**服务端**做（`.where({_serverTs: cmd.gte(new Date(since))})`，
  `cloudbaseAdapter.js:381`）。全局只有一个时间戳的话，服务端无法逐条回答「你在不在区间里」，
  只能全量下发。类比：文件 mtime ↔ `find -newer`、Kafka 消息 offset ↔ 消费者提交的 offset。
- 为什么刻度不能用客户端 `updatedAt`：一台时钟快的设备会把水位线推到**未来**，
  那段时间里其他设备的写入 `updatedAt < 水位线` ⇒ **永久漏拉**（不可恢复，非延迟）。
- **接手者易混点**：设计文档术语表（45/47 行）与 7.x 三时间对照表（1883 行）虽已分别说明，
  但**没有一张图直观呈现「全局游标 vs 逐条刻度」的协作关系**。本次答疑画了两张图
  （水位线+`_serverTs` 分工 / 客户端时钟导致漏拉），**尚未补进文档**，用户如需要可转成
  mermaid 版补入 7.4 或 7.7。
- **追问②**：「已经有 `serverUpdatedAt` 为什么还要 `_serverTs`？不是同一时刻的两种表达吗？」
  → 用户的直觉**部分成立**（云函数盖刻度那一次确实写一对，注释也承认「语义干净、少一次往返」），
  但只在「成功推送」这一刻重合。留给文档的核心论据（**比现有 1883 行对照表多一列**）：
  1. **写入路径与可靠性不同**：`_serverTs` 由 `db.serverDate()`（写指令）在 `.set()` 里直接
     求值（`cloudbaseAdapter.js:503`），**每条必写**；`serverUpdatedAt` 需经 HTTP 网关调云函数
     补盖（`index.js:220`），网关/函数不可用时**静默跳过**（`isCloudApiConfigured` 为假即不写，
     函数返回空 stamps 也不报错）。⇒ **水位线不能建在可选的应用层组件上**。
  2. **`.set()` 整份覆盖会抹掉旧刻度**（`cloudbaseAdapter.js:495-501` 注释明说），所以推送已有
     文档存在「有 `_serverTs`、无刻度」的中间态；若水位线读刻度，这些文档对其他设备**永久不可见**
     （CloudBase 对缺失字段的文档不会命中 `where(gte)`）。
  3. **失效语义相反**：`serverUpdatedAt` 标「这份内容的接收时刻」，本地改一次即失效
     （`effectiveServerStamp`）；`_serverTs` 标「云端这条记录最后一次被写」，不受本地改动影响。
  4. **技术类型不同**：`_serverTs` 是平台的服务端时间类型（读回是 `Date`，必须
     `_.gte(new Date(0))` 才能比，数字 `0` 实测一条不匹配）；`serverUpdatedAt` 是明文毫秒数
     （正为能读能比、能落本地、能进备份）。
  5. **存在范围不同**：`_serverTs` 仅云端（`fromRemote` 剥掉）；`serverUpdatedAt` 落本地副本
     （`applyStamps`）—— 本地根本看不见前者。
  → 本次又画两张图（两字段职责与三处分叉条件 / 两条写入路径的可靠性对比）。**三张图均未补进文档**，
  若用户同意可一并转 mermaid 补入 7.6/7.7（三时间对照表旁），并给该表加「写入路径/可靠性」一列。
- **追问③**：「既然 `_serverTs` 不会缺失、更安全，为什么还需要 `serverUpdatedAt`？」
  → 答：**「不会缺失」这个优势只对水位线成立，对裁决一点用没有 —— 因为它压根不落本地**。
  `fromRemote()`（`merge.js:42`）第一件事就是剥掉 `_serverTs`，而裁决
  `shouldTakeRemote(localDoc, remoteDoc)` 跑在**客户端**，要**两边**各取一个刻度来比；
  本地那份里根本没有这个字段。
- 更关键的一层：`_serverTs` 之所以「永不缺失」，正因为它**只在服务端发生写入时生成** ——
  这同时意味着它**表达不了任何本地发生的事**。而裁决最核心的场景恰恰是「本地刚改的那份
  vs 云端那份」：本地写入不经过服务端 ⇒ 刻度纹丝不动 ⇒ 拿它比就永远判云端新 ⇒
  **用户刚改的被覆盖**。`serverUpdatedAt` 配 `effectiveServerStamp` 的失效判据
  （本地 `updatedAt` 越过刻度 ⇒ 刻度作废 ⇒ 退回内容时间比较）正是为这件事设计的，
  而这条判据**只对「随内容一起流动、且会被本地改动甩在身后」的字段才有意义**。
- **一句话对称总结**：`_serverTs` 是**数据库**回答「云端这条什么时候被写」
  （基础设施，永远可用，喂水位线）；`serverUpdatedAt` 是**项目自己的云函数**回答
  「这份**内容**是哪一刻的」（业务语义，尽力而为，喂裁决）。
  **别把基础设施建在可选的业务组件上（查水位线），也别拿传输层元数据做业务裁决（查裁决键）。**
- 附带差异（文档可补）：① 类型不同 —— `_serverTs` 是服务端时间对象（Date，
  查询要 `_.gte(new Date(0))`，进备份 JSON 会变 ISO 字符串）；`serverUpdatedAt` 是明文毫秒数，
  能 `Number()` 比、能落库、能进备份。② 可演进性 —— `merge.js:56-59` 注释明说
  「语义混用会让两件事都变得难以独立演进」（水位线将来想换游标机制、裁决想换向量时钟，
  绑在一起就都动不了）。
- 本次又画两张图（云端→`fromRemote`→本地的字段边界 / 本地写入后两种裁决键的结局对照）。
  至此**三轮共七张图**都**没补进文档**，是 7.6/7.7 那块最值得补的缺口。

## 概念答疑：服务端如何按 `_openid` 隔离（本轮实查）

- 用户问「服务端是如何设置按 `_openid` 做隔离的？」→ 关键结论：**隔离不在代码里**，
  由三处构成，且**都查不到源码**。
- **实查线上配置**（`queryPermissions(listResourcePermissions, resourceType='noSqlDatabase',
  resourceIds=[三个集合])`）：三个集合 `ledger_ledgers`/`ledger_bills`/`ledger_categories`
  **权限全是 PRIVATE**、**`SecurityRule` 为空** ⇒ 走的是**内置权限模板**，不是 CUSTOM 自定义规则。
  ⚠️ 这条区分很重要（见下）。注意首次不带 `resourceIds` 查返回 `resources.empty`，必须显式给集合名。
- **隔离的两半**：① 写入时 `_openid` 由 **SDK 自动注入**（客户端手写直接报错 ⇒
  `stripServerMeta()` 推送前剥所有 `_` 字段）；② 读取时由**服务端安全规则**按 `auth.openid`
  施加，客户端改不了。前端 `useLoginGate` 只是 UI 引导。
- ⚠️ **本轮最重要的发现**：CloudBase 安全规则是**验证式（validation-based）而非过滤式
  （filter-based）** —— 平台文档（`.agents/skills/cloudbase/references/cloudbase-document-database-web-sdk/
  security-rules.md` 第 19-35、640-660 行）明确：**查询条件必须是规则的子集**，系统**不会真的去取数据
  再过滤**，不含 owner 条件的查询**直接被拒**。而本项目的 `where({_serverTs: gte(since)})`
  （`cloudbaseAdapter.js:381`）**不带 `_openid`**，却线上跑得通 —— 因为用的是**简单权限 PRIVATE**
  （内置模板），与 CUSTOM 规则的验证强度不同。**⇒ 若将来收紧成 CUSTOM 规则，必须同步给所有查询
  补上 `_openid` 条件，否则 pull/push 全线 403。** 这是代码里看不出来的隐性耦合点。
- ⚠️ **云函数是管理员身份、绕过安全规则**：`ledger-sync-stamp` 的 `col.doc(id).update()`
  （`index.js:219`）只按 `_id` 定位、**不带 `_openid`**，理论上能改到别的账号的文档。项目的信任假设
  = 客户端只传自己刚 upsert 过的 `_id`（别名带账号前缀）且刻度不含业务内容。
  **云函数不属于隔离边界**，是受信任的内部组件。
- 附带：`_id` 别名（`core/cloudId.js`）与 `_openid` 是两件事 —— `_openid` 管**读**的隔离，
  `_id` 管**集合内跨账号唯一**（避 `E11000`，S4-7 真实缺陷）；别名前缀是**客户端自觉**、不承担安全职责。
- **文档缺口**（已写进 MEMORY.md 新增的「云端隔离 / 权限」一节）：`软件设计文档.md` 全文
  **没有一处**提到安全规则/PRIVATE/权限配置（grep 过，项目 md 里 0 命中），而这恰恰是**控制台里的
  隐性依赖**（代码里看不见）。这是安全相关配置，建议补一节。
